数字の出どころ

要る量はゲームのレシピをそのまま読んでいます。推測した数字はありません。

  • 段ごとの中身は SchaleDB の config.json の PotentialMaterial（25 要素）。 この配列の [i] は「i 段目に到達するぶん」ではなく「i 段目から i+1 段目へ上げるぶん」です。 到達段で引くと 5・10・15・20 段目の境目が全部 1 段ずれます
  • 裏取りとして、DB/CharacterPotentialStatExcelTable.json の RecipeId を DB/RecipeExcelTable.json → DB/RecipeIngredientExcelTable.json と辿り、 — 手順すべてを 1 つずつ突き合わせています。 クレジット・オーパーツの個数・WB の冊数が 1 か所でも食い違ったら、データを作る側で止まります
  • どのオーパーツを使うかは DB/CharacterPotentialExcelTable.json の PotentialStatGroupId を 100 で割った値。 SchaleDB 側の PotentialMaterial と — 人全員で一致しました
  • 枠は PotentialStatGroupId の下 2 桁で決まります。10 が最大 HP、 20 が攻撃力、30 が治癒力。WB もそれぞれ 応用体育 / 応用射撃 / 応用衛生 に固定です
  • 「この枠は使わない」の印は同じ表の IsUnnecessaryStat。ゲームのデータが持っている印で、 こちらで判断したものではありません（治癒力に立っている生徒が — 人います）
  • 段の上限 25 と、開放に Lv90 が要ることは Excel/ConstCommonExcelTable.json の PotentialBonusStatMaxLevelMaxHP ほかと PotentialOpenConditionCharacterLevel
  • 伸び幅は StatBonusRate。1 段あたり 20 で、10000 分率なので 0.2%、25 段で 5% です。 25 段ぶん全部を数えて、段 × 20 になっていることを確かめています。 掛け方は SchaleDB 本体の計算に合わせました —— あちらの JavaScript が Math.round(基礎値(Lv) × 段数 × 0.002) としていて、 0.002 は 20 / 10000 と同じです （schaledb.com の assets/StudentListModal-*.js。2026-08-30 に読みました）
  • 基礎値の出し方も同じところから。Lv1 と Lv100 の 2 点を 基礎値 = round(Lv1 + (Lv100 − Lv1) × (Lv − 1) / 99) で結んでいます。 ★の倍率は掛けません。SchaleDB も潜在能力ぶんは★を掛ける前の値から数えています

オーパーツと応用 WB の入手先は出していません。ステージのドロップを 320 本ぜんぶ当たりましたが、 「◯◯の欠片」も応用 WB も 1 本も落ちてきませんでした。裏が取れないので書かないことにしています。 手持ちの数は自分で入れる形にしました。

出典 — electricgoat/ba-data（レシピ・枠・上限）、 SchaleDB（段ごとの中身、生徒と道具の名前、顔の絵、伸びの掛け方）。取得は —。
